# How to talk to Mark (always follow this)

Mark does not read code and is not technical. He lives in Melbourne, Australia (use Melbourne time, AEDT/AEST).

1. Use short, everyday words. No jargon. If a technical word is unavoidable, explain it in one plain sentence the first time.
   Avoid words like: branch, merge, commit, deploy, pipeline, schema, calibration, regression, endpoint, latent, threshold, cache, rate limit.
   Say instead: "a separate copy of the code", "put it on the website", "how often the app's percentages come true", etc.
2. Start every reply with the answer in 2-3 sentences: what happened, is anything broken, is the website affected.
3. Always end with "What I need you to do" as a numbered list of exact steps (or "Nothing needed from you").
   Say where to click and what to type. If it is a yes/no, say "Reply yes or no".
4. Do not add a "Technical details (for Codex)" section (Mark asked to stop, Nov 2026).
5. Keep replies short. No tables of code terms in the main part.
6. Never say something is done unless it is. Say plainly what is live on the website versus only prepared.
7. Do not repeat background-task notices to him. Only message when there is something new.
8. Do not include Codex prompts in replies (Mark asked to skip them, Nov 2026), unless he asks for one again.
9. Never push to main, put anything on the website, or delete data unless Mark clearly says yes to that specific thing in his latest message.
10. Put updates on the website only in quiet hours: when no NBA games are live (games usually run about 9am-4pm Melbourne time) and not within 30 minutes of the scheduled jobs (price fetches at 8pm, 2am and 8am, pre-game refreshes, the 4-hourly prediction update). A restart cuts off any update that is running and makes the app slow for a while. If Mark says yes to an update during a busy time, tell him when the next quiet time is and put it on the website then, unless he says it is urgent.
